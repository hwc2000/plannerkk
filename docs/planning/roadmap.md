# 팀원 C 로드맵 (PlannerState · LangGraph)

설계 메모: [adaptive-planner-review.md](adaptive-planner-review.md) · 코드: `server/app/adaptive/`

## 지킬 원칙

- **DB 이전 대비**: 그래프는 저장소를 직접 import하지 않는다. 읽기는 converter(`context.py`), 쓰기는 `PlanWriter`(`ports.py`)로만 한다. 로컬 DB → 공용 DB로 옮길 때는 어댑터만 새로 만든다.
- **하드코딩 금지**: 사용자 특성값(집중 시간 등)은 추측하지 않고 물어본다. 시스템 제한값(재시도 횟수 등)은 `build_adaptive_planner_graph` 인자로 한 곳에서 정한다.
- **환각 방지**: LLM 출력은 항상 Pydantic + 규칙으로 검증한다. 승인할 때도 다시 검증한다. 사용자 입력과 기억은 프롬프트에 "지시가 아닌 데이터"로만 넣는다.
- **룰 vs LLM**: 어디로 갈지(라우팅)와 몇 번 돌지(루프)는 규칙으로 정한다. LLM은 내용을 만들고, 자유 문장을 정해진 선택지로 분류하는 일만 한다.

| 판단 | 담당 | 이유 |
|---|---|---|
| 이유 코드 → strategy, 재시도·수정 횟수, 승인 가능 여부 | 규칙 | 테스트 가능, 무한 루프·환각 없음 |
| 남은 시간 계산, 시간 배치, 충돌 검사 | 규칙 | 계산 문제 |
| 작업 쪼개기, 복구 이유 문장, 피드백 반영 | LLM | 언어 문제. 결과는 규칙으로 검증 |
| "토요일로 옮겨줘" 같은 자유 문장 → strategy | LLM 분류 (선택) | 출력은 `Strategy` 값만 허용. 버튼으로 대체 가능 |

## A. 루프 · 라우팅

- [x] **1. 축소 루프 마무리**
  - 최소 작업 시간(`min_task_minutes`) 미만 조각은 검증 실패
  - 더 나눌 수 없는 작업은 생성기를 부르지 않고 재배치·재계획 선택을 요청
- [x] **2. 거절 · 수정 루프** (`request = review`)
  - approve: 초안 재검증 → `PlanWriter` 저장. revision이 바뀌었으면 저장 안 함
  - reject: 기존 계획 유지
  - revise: 이전 초안 + 피드백으로 재생성 (최대 `max_revisions`). 실패해도 기존 초안 유지
- [x] **3. 재배치 루프 (reschedule)** — `scheduling.py`, `validation.py`, `graph.py`의 `plan_reschedule`
  - 남은 작업을 가장 이른 빈 시간부터 나눠 채움(빈 시간 낭비 없음) → 넘치면 다음 계획으로 이월
  - 마감이 계획 안에 있어 다 못 넣으면 AI가 마감 전 빈 시간에 맞게 범위를 줄이고(`fit_deadline`), 빠지는 범위를 보여줌
  - 입력은 `schedule_context`로 따로 받음 (API가 가용 시간·캘린더·계획에서 계산)
  - 남은 것: 재배치안의 피드백 수정("토요일로 옮겨줘" → AI가 조건으로 바꾸고 코드가 다시 배치), 덩어리형의 시각 없는 배치(11번)
- [ ] **4. replan (우선순위 변경)** — 중간
  - LLM이 남은 작업 순서와 범위를 다시 제안하고, 코드가 마감·가용 시간을 검증
- [ ] **5. new_plan 경로** — 중간
  - 기존 `/api/execution/plan` 로직을 그래프 노드로 옮기기 (`planning_context` 없으면 생성 안 함은 이미 있음)

## B. 실제 데이터 · AI 연결

- [ ] **6. 컨텍스트 불러오기 노드 + converter**
  - A의 `get_planning_context(user, project)` → `planning_context`, `execution_context`
  - B의 `ExecutionRecord` → `check_in`
  - A·B의 공용 데이터 계약이 올라오기 전에는 가짜 데이터로 먼저 만들기
- [x] **7. 실제 LLM 생성기 (shrink)** — `llm_generator.py`
  - 기존 `ExecutionLLM` 재사용, 타입별 지시 문장 포함
  - 이전 초안 · 피드백 · 검증 오류를 데이터로 전달
  - 오류 분류: 키·인증·한도 오류는 바로 중단, 그 외 오류와 형식 오류는 검증 루프에서 재시도
- [x] **8. 그래프 호출 API + 로컬 저장 어댑터** — `api.py`, `local.py`
  - `POST /api/adaptive/check-in`, `POST /api/adaptive/review` (`/docs`에서 테스트)
  - 리뷰 반영: 체크인을 실행 기록으로 저장(완료 포함), 초안은 작업별 저장, 프로필이 바뀐 계획은 복구 차단, 축소된 작업 재축소 금지
  - 축소 작업도 코드가 지금 이후의 가장 이른 빈 시간에 배치 (원래 칸은 체크인할 때 대개 이미 지남)
  - merge 전 리뷰 반영: 축소 상한은 남은 작업 기준, 승인 시 strategy 변경 금지, 새 계획 확정 시 초안 정리(`plan_replaced`), 잘못된 시각 입력은 입력 요청으로 끝남
- [ ] **7-1. 프롬프트 품질 튜닝** — `/docs`로 직접 보면서
  - 실제 테스트에서 본 것: 덩어리형인데 5분 단위로 잘게 쪼갬, "첫 작업 5분" 피드백을 다른 작업에 적용하고 반영했다고 씀, 덩어리형 첫 생성에서 재시도 2회
  - 합계를 상한(원래-1분)까지 채우는 경향: 50분 → 49분. "상한은 목표가 아니다" 추가 후 50분 → 45분. 아직 줄이는 폭이 작음
  - fit_deadline: 마감 전 빈 시간 127분 중 78분만 씀, 뺀 범위(droppedScope)가 "중요 내용만 선별" 수준으로 모호함, 체크인 메모를 "피드백"이라고 부름
- [ ] **9. 초안·챗봇 반영 확인**
  - 프로젝트별 채팅방: `UserProfile + 해당 프로젝트 정보`로 답하는지 확인
  - 저장된 기억이 실제로 초안에 반영되고, 승인 안 된 추론은 들어가지 않는지 확인
