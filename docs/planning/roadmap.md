# 팀원 C 로드맵 (PlannerState · LangGraph)

설계 메모: [adaptive-planner-review.md](adaptive-planner-review.md) · 코드: `server/app/adaptive/`

## 지킬 원칙

- **DB 이전 대비**: 그래프는 저장소를 직접 import하지 않는다. 읽기는 converter(`context.py`), 쓰기는 `PlanWriter`(`ports.py`)로만 한다. 로컬 DB → 공용 DB로 옮길 때는 어댑터만 새로 만든다.
- **하드코딩 금지**: 사용자 특성값(집중 시간 등)은 추측하지 않고 물어본다. 시스템 제한값(재시도 횟수 등)은 `build_adaptive_planner_graph` 인자로 한 곳에서 정한다.
- **환각 방지**: LLM 출력은 항상 Pydantic + 규칙으로 검증한다. 승인할 때도 다시 검증한다. 사용자 입력과 기억은 프롬프트에 "지시가 아닌 데이터"로만 넣는다.
- **룰 vs LLM**: 어디로 갈지(라우팅)와 몇 번 돌지(루프)는 규칙으로 정한다. LLM은 내용을 만들고, 자유 문장을 정해진 선택지로 분류하는 일만 한다.

| 판단 | 담당 | 이유 |
|---|---|---|
| 이유 코드 → strategy, 재시도·수정 횟수, 승인 가능 여부 | 규칙 | 테스트 가능, 무한 루프·환각 없음 |
| 남은 시간 계산, 시간 배치, 충돌 검사 | 규칙 | 계산 문제 |
| 작업 쪼개기, 복구 이유 문장, 피드백 반영 | LLM | 언어 문제. 결과는 규칙으로 검증 |
| "토요일로 옮겨줘" 같은 자유 문장 → strategy | LLM 분류 (선택) | 출력은 `Strategy` 값만 허용. 버튼으로 대체 가능 |

## A. 루프 · 라우팅

- [x] **1. 축소 루프 마무리**
  - 최소 작업 시간(`min_task_minutes`) 미만 조각은 검증 실패
  - 더 나눌 수 없는 작업은 생성기를 부르지 않고 재배치·재계획 선택을 요청
- [x] **2. 거절 · 수정 루프** (`request = review`)
  - approve: 초안 재검증 → `PlanWriter` 저장. revision이 바뀌었으면 저장 안 함
  - reject: 기존 계획 유지
  - revise: 이전 초안 + 피드백으로 재생성 (최대 `max_revisions`). 실패해도 기존 초안 유지
- [x] **3. 재배치 루프 (reschedule)** — `scheduling.py`, `validation.py`, `graph.py`의 `plan_reschedule`
  - 남은 작업을 가장 이른 빈 시간부터 나눠 채움(빈 시간 낭비 없음) → 넘치면 다음 계획으로 이월
  - 마감이 계획 안에 있어 다 못 넣으면 AI가 마감 전 빈 시간에 맞게 범위를 줄이고(`fit_deadline`), 빠지는 범위를 보여줌
  - 입력은 `schedule_context`로 따로 받음 (API가 가용 시간·캘린더·계획에서 계산)
  - 남은 것: 재배치안의 피드백 수정("토요일로 옮겨줘" → AI가 조건으로 바꾸고 코드가 다시 배치), 덩어리형의 시각 없는 배치(11번)
- [ ] **4. replan (우선순위 변경)** — 중간
  - LLM이 남은 작업 순서와 범위를 다시 제안하고, 코드가 마감·가용 시간을 검증
- [ ] **5. new_plan 경로** — 중간
  - 기존 `/api/execution/plan` 로직을 그래프 노드로 옮기기 (`planning_context` 없으면 생성 안 함은 이미 있음)

- [ ] **7-1. 프롬프트 품질 튜닝** — `/docs`로 직접 보면서
  - 실제 테스트에서 본 것: 덩어리형인데 5분 단위로 잘게 쪼갬, "첫 작업 5분" 피드백을 다른 작업에 적용하고 반영했다고 씀, 덩어리형 첫 생성에서 재시도 2회

  - fit_deadline: 마감 전 빈 시간 127분 중 78분만 씀, 뺀 범위(droppedScope)가 "중요 내용만 선별" 수준으로 모호함, 체크인 메모를 "피드백"이라고 부름

  - 프로젝트별 채팅방: `UserProfile + 해당 프로젝트 정보`로 답하는지 확인

## 임시 메모
재배치 루프 만들었어. 백엔드 테스트 111개가 통과했고, 실제 AI로도 처음부터 끝까지 돌려봤어(임시 DB라 네 DB는 그대로야). 커밋은 아직 안 했어.

동작 방식
체크인 이유가 시간 부족, 방해받음, 예상보다 큼이면 재배치로 가.

상황	처리	누가
남은 작업이 빈 시간에 다 들어감	가장 이른 빈 시간부터 채움	코드
넘치는데 마감이 이번 계획 이후	들어가는 만큼 배치하고 나머지는 다음 계획으로 넘김	코드
넘치는데 마감이 이번 계획 안	마감 전 빈 시간에 맞게 무엇을 남기고 뺄지 정함	AI
위 경우에 AI가 범위를 정한 뒤	그 작업들을 빈 시간에 배치	코드
마감 전 빈 시간이 아예 없음	재계획을 고르라고 요청	코드
네가 말한 "빈 시간 낭비 금지"

60분짜리 작업에 오늘 빈 시간이 50분이면, 오늘 50분 + 다음 빈 시간 10분으로 나눠. 60분이 들어갈 자리를 기다리지 않아.
남는 조각이 5분보다 짧으면 이상하니까, 그럴 땐 앞 조각을 살짝 줄여서 마지막 조각을 5분 이상으로 맞춰.
계획의 여유분(buffer)도 빈 시간으로 써. 원래 이런 복구에 쓰라고 남겨둔 시간이라서야.
깐깐형은 조각마다 집중 시간 이하로 자르고, 사이에 휴식 시간을 둬.
AI가 왜 필요한지 보여주는 부분
마감까지 시간이 부족할 때 "무엇을 남기고 무엇을 뺄지"는 규칙으로 정할 수 없어서 AI가 맡아. AI는 내용만 정하고, 시간 배치와 검증은 항상 코드가 해. 이번에 빼기로 한 범위(droppedScope)는 사용자에게 보여줘서 직접 판단할 수 있게 했어.

실제 AI 테스트 결과
조건: 덩어리형 사용자, 월·수 18~21시 가용, 마감 수요일

방해받음 (30분 작업): AI 없이 0초. 월 19:30~20:00 빈 시간(원래 여유분)으로 옮겼어.
예상보다 큼 (남은 240분, 마감 수요일): AI가 "중요 내용 선별 30분 → 슬라이드 1~3장 초안 48분"으로 범위를 줄였어. 코드가 월 20:00, 수 19:53에 배치했어.
테스트하다가 하나 더 고쳤어. 승인 안 한 초안 두 개가 같은 빈 시간(월 19:40)을 동시에 차지했어. 이제 다른 작업의 승인 대기 초안이 잡은 시간도 빈 시간에서 빼.

그 밖에 막아둔 것

사용자가 "이 시간엔 못 해요"라고 했으니 작업의 원래 자리는 빈 시간에서 빼.
승인할 때 빈 시간을 다시 계산해서, 그사이 지나간 시각이나 겹치는 일정이 있으면 저장하지 않아.
아직 부족한 점 (로드맵에 적어둠)
AI 결과 품질 (7-1번):
마감 전 빈 시간 127분 중 78분만 썼어.
뺀 범위 설명이 "중요 내용만 선별" 수준으로 모호해.
체크인 메모를 "피드백"이라고 불렀어.
재배치안은 피드백으로 수정이 안 돼. "토요일로 옮겨줘"를 AI가 조건으로 바꾸고 코드가 다시 배치하는 건 다음 단계야. 지금은 그 요청을 받으면 기존 초안을 유지하고, 승인·거절하거나 축소로 바꾸라고 안내해.
덩어리형도 아직 시각 단위로 배치돼. 시각 없이 날짜·덩어리로만 잡는 건 11번이야.
직접 써보려면
내가 띄웠던 서버는 꺼진 상태라 네 터미널에서 .venv/bin/python run_local.py로 띄우고 /docs에서 테스트하면 돼.

체크인할 때 reasonCode를 time_shortage, interruption, underestimated 중 하나로 보내.
필요하면 remainingMinutes(남은 작업 시간)와 events(캘린더 일정)도 같이 보내.
이 사용법과 흐름은 설계 메모에, 진행 상황은 로드맵에 반영해뒀어.
